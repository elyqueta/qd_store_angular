# 05 · Internacionalização (Transloco)

Decisão D-004: **Transloco** (runtime, troca de idioma sem recarregar).

## Configuração
- Idiomas: `pt` (padrão, pt-AO/pt-PT) agora; `en` no futuro, só acrescentar `en.json` e registar em `availableLangs`.
- Ficheiros: `src/assets/i18n/pt.json` (global) e **scopes lazy por feature**: `assets/i18n/<feature>/pt.json`.
- Idioma ativo persistido em `localStorage` (`qd.lang`) e refletido em `<html lang>`.
- SSR: o loader deve conseguir ler os JSON no servidor (URL absoluta ou leitura de ficheiro) — validar na Fase 0.

## Regras
1. Chaves em inglês, estáveis, hierárquicas: `catalog.product.addToCart`, `auth.login.title`.
2. Nada de concatenar frases; usar parâmetros: `"greeting": "Olá, {{name}}"`.
3. Plurais e datas/moedas via `Intl` com o locale ativo (`Intl.NumberFormat('pt-AO', { style:'currency', currency:'AOA' })`).
4. Mensagens de validação de formulário também traduzidas.
5. **Erros da API:** hoje o back-end devolve `message` em pt-PT sem código. Estratégia: mapear por **status HTTP** e por `details[].field` para chaves i18n; usar o `message` da API só como fallback. Pedir ao back-end códigos de erro estáveis (lacuna L-04).
6. Conteúdo vindo da BD (nomes/descrições de produtos, categorias) **não** é traduzido nesta fase.
7. SEO multilíngue (`hreflang`, URLs por idioma) fica para quando existir `en`; deixar o `SeoService` preparado para receber o idioma.
